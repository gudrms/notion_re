1. 서비스 MSA 변환 프로젝트
   📅 기간 : 2024.06 ~ 2025.06 (12개월)
   👥 팀 구성 : 5명
   🎯 역할 : 팀원 (백엔드 & 프론트엔드 담당)
   🛠 기술 스택
- **Backend** : Java 8 → 17,Nest.js Spring Boot 2.6.6, Spring Data JDBC, MyBatis, Oracle, Postgres
- **Frontend** : TypeScript, Next.js, JavaScript,
- **인증** : Keycloak SSO + Spring Security (JWT)
- **인프라** : Docker, GitLab CI/CD, Batch
- **모니터링** : 자체 로그 분석기, Trace ID 기반 분산 추적, 실시간 대시보드(APM)
- **캐싱** : Redis (마스터 데이터, 세션)

### **🎯 프로젝트 배경 및 목표**

기존 Java/JSP 모놀리식 홈페이지에 내장된 서비스들(식권, 전자동의서, 문진표, 예약 등)이 하나의 코드베이스에 밀집되어 있어 다음과 같은 문제가 있었음:

| **문제** | **상세** |
| --- | --- |
| **유지보수 효율 저하** | 식권 로직 수정 시 전체 빌드·배포 필요, 배포 주기 1주 |
| **장애 전파** | 한 서비스 장애(예: 식권 정산 배치)가 전체 시스템에 영향 |
| **확장성 한계** | 피크 타임(오전 06:40~07:40) 트래픽 집중 시 전체 시스템 부하 |
| **기술 부채** | Java 8 + JSP 환경에서 신규 기술 도입 제한 |

**목표**: 도메인 기반으로 서비스를 분리하여 독립 배포·확장 가능한 MSA 아키텍처로 전환

📋 주요 업무

**1. 서비스 분리 설계 및 구현**

- 기존 모놀리식 시스템을 도메인 기반 5개 서비스로 분리
    - **예약 서비스**: 모든 서비스의 시작점, ACID 보장 (로컬 트랜잭션)
    - **식권 서비스**: 독립 서비스 분리, 배치 기반 정산 자동화 (8개 센터 데이터 집계)
    - **전자동의서 서비스**: PDF 생성(Puppeteer 기반 PDF 생성) + 전자서명, PL 총괄
    - **문진표 서비스**: 동적 폼 생성, 의료진 검토 워크플로우, 조건부 검증 로직 이관
    - **인증 서비스**: Keycloak SSO 도입으로 파편화된 인증 방식 통합 표준화
- Java 8 → 17 버전 업그레이드 (서비스 분리와 동시 진행)

**2. 아키텍처 설계 의사결정**

| **결정 사항** | **선택** | **이유** |
| --- | --- | --- |
| **전환 방식** | 빅뱅 전환 (병행 개발 후 일괄 교체) | 기술 스택이 다르고(Java 8→Java 17, Nest.js), 세션/인증 방식이 달라 기존 시스템과 공존 제한 |
| **DB 전략** | Shared DB + 논리적 분리 | 5개 서비스가 '수검자' 데이터를 공통 참조, 물리 분리 시 네트워크 오버헤드 과다 |
| **통신 방식** | REST API 동기 통신 | 현재 규모(5개 서비스)에서 메시지큐 도입은 인프라 복잡도 대비 이점 부족 |
| **데이터 소유권** | 쓰기는 도메인 서비스만, 읽기는 API를 통해서만 | 향후 물리적 DB 분리 시 마이그레이션 비용 최소화 |

**3. 분산 환경 모니터링 구축**

- 모든 서비스 간 통신에 **Trace ID** 전파하여 요청 흐름 추적
- **로그 분석기 자체 개발**:  지연 구간 자동 검출
- 대형 모니터에 실시간 로그 대시보드 구성 → 오류 발생 즉시 인지

**4. 성능 최적화**

- **Redis 캐싱**: 마스터 데이터(의료 서식, 센터 정보) 캐싱으로 DB 부하 분산
- **API 응답 최적화**: 불필요한 서비스 간 호출을 줄이기 위해 응답에 필요 데이터 일괄 포함
- **결과**: 동의서 피크 타임 응답 속도 **80% 개선 (3초 → 0.5초)**

**5. 데이터 정합성 전략**

- **핵심 데이터(예약)**: 단일 DB 트랜잭션으로 ACID 보장 (강한 일관성)
- **하위 서비스(문진, 동의서 등)**: 최종 일관성(Eventual Consistency) 기반으로 설계하여, 일부 서비스 장애가 전체 흐름에 영향을 주지 않도록 분리

**6. 배포 파이프라인 구축**

- Docker 컨테이너화로 서비스별 독립 배포 가능
- GitLab CI/CD 파이프라인 서비스별 구성
- API 변경 시 하위 호환성 유지 규칙 적용 (신규 필드는 optional 추가)

### **🔥 기술적 도전 및 해결**

**① 레거시 비즈니스 로직 이관 시 검증 누락**

- **문제**: 문진표 조건부 검증(Validation) 로직이 기존 코드에 하드코딩 + 문서화 없음 → 일부 조건 분기 누락
- **해결**: 기존 시스템 Validation 로직 역추적 → 검증 규칙 명세서 작성 → **패리티 테스트(Parity Test)** 도입 (동일 입력 → 동일 출력 비교 검증)
- **교훈**: 전환 전 레거시 로직 명세화를 먼저 완료해야 함

**② 데이터 마이그레이션 타임존 이슈**

- **문제**: Oracle(서버 KST 고정) → 이관 시 KST/UTC 혼용으로 시간 9시간 어긋남 발생
- **해결**: 마이그레이션 스크립트에 `AT TIME ZONE 'Asia/Seoul'` 변환 추가, 날짜 경계 데이터(23시, 0시) 집중 검증 드라이런 수행
- **교훈**: 마이그레이션 체크리스트에 '타임존 검증' 항목 필수 추가

**③ Shared DB에서 서비스 간 데이터 소유권 경계**

- **문제**: 5개 서비스가 '수검자' 테이블을 공통 참조 → 누가 어떤 데이터를 수정할 수 있는지 불명확
- **해결**: '쓰기 권한은 도메인 서비스만, 읽기는 API를 통해서만' 규칙 확립 → 논리적으로 DB per Service처럼 동작
- **향후 계획**: 서비스 10개 이상 확장 시 물리적 DB 분리 + CQRS 패턴 도입 예정

**④ 분산 환경 디버깅 복잡도**

- **문제**: 요청 하나가 여러 서비스를 거치면서 어디서 문제가 생겼는지 추적 어려움
- **해결**: Trace ID 기반 분산 추적 + 자체 로그 분석기(1초 이상 지연 자동 검출) + 실시간 대시보드
- **향후 계획**: ELK(Elasticsearch+Logstash+Kibana) 또는 Jaeger 도입으로 체계화
